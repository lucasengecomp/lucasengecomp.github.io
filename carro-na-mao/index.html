Carro na Mão

App Android em Flutter para controle de veículos — abastecimentos, manutenções, despesas recorrentes e lembretes. V1.0.0 em produção, distribuído direto aos usuários via GitHub Releases com APK assinado por pipeline próprio no GitHub Actions.

Repositório → Download v1.0.0 → Política de privacidade

Contexto

Três pessoas próximas queriam acompanhar o custo real dos próprios carros — abastecimentos, consumo médio, manutenções e lembretes de revisão. Não havia necessidade de nuvem, multi-usuário no mesmo device nem sincronização entre pessoas; cada um é dono do seu próprio dado. O desafio foi construir um app estável, bonito e distribuível sem passar por lojas de aplicativo nesta fase inicial.

Stack & decisões técnicas

  • Flutter + Dart para um codebase único que serve Android hoje e habilita web (iOS via PWA) amanhã.
  • Drift (SQLite tipado) para persistência local — zero backend na V1, dados sempre disponíveis offline.
  • Riverpod como camada de estado, com providers reativos acoplados ao Drift.
  • go_router para navegação declarativa, preparada para deep links futuros.
  • flutter_local_notifications para lembretes de manutenção, com agendamento inexato (Doze-mode friendly) pra evitar o SecurityException: SCHEDULE_EXACT_ALARM do Android 12+.
  • fl_chart para o dashboard de consumo e gastos, com paleta adaptada a dark mode.
  • +840 testes (unitários, de widget e de DAO) rodando no CI a cada PR.

Pipeline de release

A V1 foi distribuída sem Google Play (decisão de produto baseada em custo e cadência). O fluxo ficou:

  1. git tag v1.0.0 && git push origin v1.0.0
  2. GitHub Actions decodifica o keystore de um secret em base64, gera key.properties no runner, builda flutter build apk --release.
  3. APK assinado é anexado a um draft release com instruções de instalação embutidas (vindas de docs/release/instalar-apk.md) e changelog auto-gerado.
  4. Após revisão manual, o release é publicado e o link é compartilhado diretamente com os usuários.
  5. Updates futuros preservam dados nos devices porque a assinatura é estável — mesmo keystore, APK por APK.

Keystore, senhas e key.properties nunca entram no repositório; o workflow só referencia nomes de secrets. A assinatura foi validada byte-a-byte comparando apksigner verify --print-certs entre o build local e o build do CI.

Arquitetura planejada para a V2

Um dos três usuários é iOS. Em vez de pagar a taxa anual de Apple Developer nesta fase de validação, a V2 atende esse usuário via Flutter Web deployado no Vercel com persistência em Supabase (Postgres + magic link + RLS por user_id). Os usuários Android continuam no Drift local. Como não há sincronização entre as duas realidades (por design do produto), a arquitetura é desacoplada por uma camada Repository com duas implementações, selecionadas por kIsWeb no composition root.

O que ficou de aprendizado

  • Devices reais importam. O bug crítico do SCHEDULE_EXACT_ALARM só apareceu num Galaxy S22 com Android 16 — testes e analyze passavam limpos. CI não substitui device físico.
  • Major bumps antes de release têm custo. Subir fl_chart 0.70 → 1.3 e cupertino_icons 1 → 2 entrou em PR próprio, validado em device, antes do primeiro release — e não bundled com o release.
  • Keystore é ativo crítico. Perdê-lo quebra a continuidade de updates nos devices dos usuários. Fora do repo, backup externo, senhas em gerenciador.
  • Instruções de instalação são parte do produto. O texto de docs/release/instalar-apk.md é copiado automaticamente para o corpo de cada release — os usuários não precisam ler documentação separada.
